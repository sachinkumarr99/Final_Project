# Online Verification Frontend API Specification

This document is a frontend-ready contract for the Spring Boot backend of the Legal Metrology Online Verification project. It captures the real endpoint paths, request payload shapes, response payloads, status codes, validation rules, enums, and authentication expectations.

## 1. Base Configuration

- Base URL (local dev): `http://localhost:8080`
- Security: JWT-based authentication is enabled.
- Public endpoints: `/public/**` are open.
- Protected endpoints: all other routes require `Authorization: Bearer <token>` header.
- Admin-only route: `/admin/**` requires role `ADMIN`.

### Common Auth Header

```http
Authorization: Bearer <jwt_token>
```

### Common Response Format

Most user-related endpoints return a wrapped response object:

```json
{
  "success": true,
  "message": "Operation successful",
  "data": {}
}
```

For error handling, the backend uses a standard error body:

```json
{
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "apiPath": "/user/register_instrument",
  "timestamp": "2026-08-29T10:00:00"
}
```

## 2. Authentication and User APIs

## 2.1 Public Registration

### POST `/public/register`

Register a business user.

#### Request body

```json
{
  "email": "user@example.com",
  "mobile": "9876543210",
  "password": "Abcd@1234",
  "firstName": "Sachin",
  "lastName": "Kumar",
  "address": "12 Market Road",
  "city": "Delhi",
  "state": "Delhi",
  "isOrganization": false
}
```

#### Validation rules

- `email`: required, valid email format
- `mobile`: required, 10-digit numeric string
- `password`: required, minimum 8 chars, must include uppercase, lowercase, number and special character
- `firstName`: only letters, 2–10 chars
- `lastName`: only letters, 2–20 chars
- `address`: 5–200 chars
- `city`: alphabetic only, 2–15 chars
- `state`: alphabetic words separated by spaces
- `isOrganization`: boolean

#### Success response

- Status: `201 Created`
- Body:

```json
"User Registerd Successfully"
```

#### Failure response

- `409 Conflict` if email already exists
- `400 Bad Request` if validation fails

---

### POST `/public/signIn`

#### Request body

```json
{
  "email": "user@example.com",
```

#### Success response

- Status: `200 OK`
- Body:

```json
"eyJhbGciOiJIUzI1NiJ9..."
```

#### Failure response

- `401 Unauthorized` if credentials are invalid

## 2.2 User APIs

### POST `/user/register_instrument`

Register a new measuring instrument for the logged-in user.

#### Request body

```json
{
  "instrumentType": "WEIGHING_MACHINE",
  "manufacturer": "Mettler Toledo",
  "model": "MT-500",
  "serialNumber": "SER-1001",
  "capacity": 500,
  "accuracyClass": "CLASS_II",
  "unit": "KILOGRAM",
  "installationLocation": "Delhi Warehouse"
}
```

#### Validation rules

- `instrumentType`: required
- `manufacturer`: required
- `model`: required
- `serialNumber`: required
- `capacity`: required, > 0
- `accuracyClass`: required
- `unit`: required
- `installationLocation`: required

#### Success response

- Status: `201 Created`

```json
{
  "success": true,
  "message": "Instrument has been registerd successfully",
  "data": {
    "instrumentNumber": "INS-2026-000001",
    "instrumentType": "WEIGHING_MACHINE",
    "status": "UNVERIFIED"
  }
}
```

#### Notes

- `instrumentNumber` is generated by the backend.
- `status` is from `Status` enum.

### POST `/user/apply_verification_instrument`

Submit a verification application for an instrument.

#### Request body

```json
{
  "instrumentNumber": "INS-2026-000001",
  "applicationType": "VERIFICATION"
}
```

#### Validation rules

- `instrumentNumber`: required
- `applicationType`: required; allowed values: `VERIFICATION` or `RE_VERIFICATION`

#### Success response

- Status: `200 OK`

```json
{
  "success": true,
  "message": "Verification Application Successfully Submitted",
  "data": {
    "applicationNumber": "APP-2026-000001",
    "instrumentNumber": "INS-2026-000001",
    "status": "SUBMITTED"
  }
}
```

#### Important business rules

- Instrument must exist.
- Application for same instrument cannot already exist.
- Required documents must be uploaded before submission:
  - `INSTRUMENT_PHOTO`
  - `PURCHASE_INVOICE`
  - `MANUFACTURER_DOCUMENT`

```json
{
```

- `scheduledDate`: required, cannot be in the past

#### Success response

```json

  "id": "64f5ad1ed1b8e2e9d0a1b2ca",
```

### POST `/lmo/applications/{applicationNumber}/verify`

Submit actual verification readings for an instrument and mark the result as approved or rejected.

#### Example

```http
POST /lmo/applications/APP-2026-000001/verify
```

#### Request body

```json
{
  "readings": [
    {
      "testValue": 10,
      "actualValue": 10.2
    },
    {
      "testValue": 20,
      "actualValue": 19.8
    }
  ]
}
```

#### Validation rules

- `readings`: required and not empty
- each reading must contain:
  - `testValue` required
  - `actualValue` required

#### Success response

```json
{
  "id": "64f5b0d1d1b8e2e9d0a1b2cb",
  "applicationNumber": "APP-2026-000001",
  "instrumentNumber": "INS-2026-000001",
  "lmoId": "lmo_123",
  "readings": [
    {
      "testValue": 10,
      "expectedValue": 10,
      "actualValue": 10.2,
      "error": 0.2,
      "permissibleError": 0.5,
      "passed": true
    },
    {
      "testValue": 20,
      "expectedValue": 20,
      "actualValue": 19.8,
      "error": -0.2,
      "permissibleError": 0.75,
      "passed": true
    }
  ],
  "result": "APPROVED",
  "verifiedAt": "2026-08-29T11:00:00"
}
```

#### Business logic

- Backend looks up the configured verification standard for the instrument type.
- Verifies each `testValue` against the standard config.
- Calculates `error = actualValue - expectedValue`.
- Marks each reading as `passed` if `abs(error) <= permissibleError`.
- If all readings pass, the final result is `APPROVED`.
- Otherwise, final result is `REJECTED`.
- The instrument status is updated to `VERIFIED` or `REJECTED`.

## 5. Document Upload APIs

### POST `/documents/instrument/upload_with_categories`

Upload one or more instrument-related documents to Cloudinary and store metadata in MongoDB.

#### Required form-data fields

```http
instrumentNumber: INS-2026-000001
categories: INSTRUMENT_PHOTO
categories: PURCHASE_INVOICE
categories: MANUFACTURER_DOCUMENT
files: <file1>
files: <file2>
files: <file3>
```

#### Allowed categories

- `INSTRUMENT_PHOTO`
- `PURCHASE_INVOICE`
- `MANUFACTURER_DOCUMENT`
- `PREVIOUS_VERIFICATION_CERTIFICATE`

#### Success response

```json
[
  {
    "category": "INSTRUMENT_PHOTO",
    "originalFileName": "photo.jpg",
    "cloudinaryPublicId": "INSTRUMENT_PHOTO_1724758000_a1b2c3d4",
    "fileUrl": "https://res.cloudinary.com/.../photo.jpg",
    "fileFormat": "image/jpeg",
    "fileSizeInByte": 123456
  },
  {
    "category": "PURCHASE_INVOICE",
    "originalFileName": "invoice.pdf",
    "cloudinaryPublicId": "PURCHASE_INVOICE_1724758001_b2c3d4e5",
    "fileUrl": "https://res.cloudinary.com/.../invoice.pdf",
    "fileFormat": "application/pdf",
    "fileSizeInByte": 456789
  }
]
```

#### Important rules

- `files.length` must equal `categories.length`.
- Each category can only be uploaded once for the same instrument.
- The instrument must already exist.
- This route is protected by JWT authentication.

## 7. Frontend Implementation Notes

### Recommended API flow

1. User registration: `POST /public/register`
2. User login: `POST /public/signIn`
3. Store JWT in frontend app storage (`localStorage` or secure cookie)
4. Add header for protected requests:

```js
axios.defaults.headers.common['Authorization'] = `Bearer ${token}`;
```

### Typical frontend state shape

```ts
interface AuthState {
  token: string;
  user: {
    email: string;
    role: string;
    id: string;
  };
}
```

### Recommended UI modules

- Auth: register, login
- User dashboard: instrument list, application list
- Admin dashboard: register LMO, register organization, assign application, create standards
- LMO dashboard: assigned applications, schedule verification, submit readings
- Document upload: document categories and file inputs

## 8. Known Observations for Frontend Team

- Some endpoints return plain strings instead of structured JSON envelopes.
- Some routes are named with underscores, e.g. `/admin/register_LMO` and `/admin/register_Organization`.
- `Authorization` is required on almost all non-public APIs.
- `/public/**` is allowed without auth.
- `/admin/**` is restricted to `ADMIN` authority.
- The application uses MongoDB and Cloudinary; document-upload endpoints are not purely JSON endpoints and use `multipart/form-data`.
- A few response messages contain typos, e.g. “Registerd Successfully” instead of “Registered Successfully”.
